# Scientific Authority Receipts

**Status:** canonical receipt-time authorization journal

Receipt time is generated by the governed service and cannot be supplied or backdated by clients.

A scientific event signature proves control of the event signing key. It does not, by itself, prove that the key was bound to the named actor or that the actor had authority to perform the scientific action. Mycelix-DeSci therefore records a second signed object for every accepted canonical event: the scientific authority receipt.

## What a receipt binds

Each receipt commits to:

- the exact scientific event ID, hash, stream, and sequence;
- the server-observed `received_at` time;
- the named actor and optional acting organization;
- the event signing public key;
- for protocol v2, the exact credential-registry revision used to resolve the actor;
- the exact authorized-key validity and revocation bounds used at acceptance;
- the actor's resolved organizations and scientific roles;
- the normalized scientific action;
- the authorization policy ID and version;
- the policy decision reason;
- a hash of the complete authority snapshot;
- the previous authority-receipt hash.

The receipt is signed by a dedicated server receipt key. The scientific actor key and receipt-service key must be distinct; receipt verification fails closed when the same key signs both objects. New registry-backed acceptances emit protocol v2 receipts and require a credential-registry record hash. That revision includes the independently signed credential acceptance timestamp. Protocol v1 remains supported only for historical receipts created before the governed registry existed.

## Two-phase journal

The authority journal uses a small two-phase protocol:

1. Validate the client event, actor/key binding, organization, and policy.
2. Create and fsync a signed pending authority receipt.
3. Append and fsync the scientific event.
4. Atomically rename the pending receipt to its committed filename.

At startup, reconciliation handles interruptions conservatively:

- a pending receipt with a matching committed event is finalized;
- a pending receipt without an event is discarded;
- a committed receipt without an event is corruption and fails startup;
- an event without a receipt before the first receipt in its stream is reported as `legacy_unattested`;
- an event without a receipt at or after receipt journaling began is reported as `unsafe_unattested`;
- receipt signatures, event bindings, and per-stream receipt chains are reverified.

This design does not claim a cross-directory filesystem transaction. It instead makes every crash point detectable and recoverable without silently inventing authority evidence.

## Historical legitimacy and revocation

Receipts preserve the authority snapshot used at the original server receipt time. A later role change or ordinary key rotation does not retroactively invalidate a legitimate historical event.

This is different from concealing a compromise. A future governed key-compromise or credential-revocation event may annotate historical risk, but it should not rewrite the original acceptance receipt.

A contiguous stream prefix written before authority receipts existed remains `legacy_unattested`. Operators may temporarily set:

```text
DESCI_ALLOW_UNATTESTED_AUTHORITY_HISTORY=true
```

This acknowledges a deployment cutover only. It does not transform those old events into receipt-attested events. It never waives an `unsafe_unattested` gap after the first receipt in a stream.

## Receipt-key rotation

Configure the current private seed with:

```text
DESCI_AUTHORITY_RECEIPT_SIGNING_KEY_FILE=/secure/authority-receipt-signing.key
```

The file must contain 32 raw bytes or 64 hexadecimal characters and must be mode `0600` or stricter on Unix.

Before changing the private key, add the old public key to a JSON trust file:

```json
[
  "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
]
```

Then configure:

```text
DESCI_AUTHORITY_RECEIPT_TRUST_FILE=/secure/authority-receipt-trust.json
```

The current private key's public key is trusted automatically. The same domain-separated service key also signs credential-registry and threshold-governance acceptance timestamps. Removing an old public key from the trust set makes historical receipts or accepted authority records signed by that key unverifiable and blocks startup when those records are present. Authorization or revocation of a governance acceptance-service key is itself a delayed threshold proposal; key validity and revocation are never backdated before the execution receipt.

## Readiness

Readiness fails when any of the following holds:

- the scientific credential registry is uninitialized, ephemeral, or below its administrator threshold;
- the receipt signing key is not configured;
- canonical event storage is ephemeral;
- pending receipts remain after reconciliation;
- legacy-unattested prefix history exists without an explicit cutover acknowledgement;
- any unsafe-unattested receipt gap exists after receipt journaling began.

The health response exposes separate checks for the event log, scientific credential registry, receipt signing, receipt journal, authority history, and legacy mutation status. `GET /api/v1/scientific/claims/{id}/authority-receipts` exports the ordered receipt chain and all unattested-event classifications for one stream.

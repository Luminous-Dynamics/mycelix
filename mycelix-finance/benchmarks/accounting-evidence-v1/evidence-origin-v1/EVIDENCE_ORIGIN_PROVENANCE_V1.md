# FIN-ACC evidence origin and transformation provenance v1

**Parent:** FIN-ACC-EVIDENCE-001 / #5798  
**Composes:** #5800 assertion matrix, #5836 assertion-purpose contract, #5790 population completeness, #5803/#5805 workpaper DAG, #5812 CAMT source artifacts.

## Purpose

Independence must not be inferred from file count, file format, collection channel or caller-provided group labels. This specification defines the evidence-origin and transformation provenance graph used to determine whether two artifacts share a material upstream origin for a named assertion and procedure.

## Core distinction

Keep these propositions separate:

1. **Artifact integrity:** exact captured bytes and transformation outputs are committed.
2. **Origin identity:** the origin/issuer/source system has a qualified identity within a declared namespace and scope.
3. **Transformation lineage:** the path from a derived artifact to the original artifacts and processing steps is complete and replayable.
4. **Independence for purpose:** two pieces of evidence do not share a material upstream origin for the proposition and procedure being assessed.

A SHA-256 digest proves byte identity relative to capture; it does not prove who created the bytes, that the origin is authentic, or that two different hashes are independent.

## Graph model

Nodes:
- `origin`: issuer, bank, supplier, custodian, source-system or independent external party;
- `artifact`: immutable invoice, statement, confirmation, report, screenshot, CSV, PDF, source export or other evidence;
- `transformation`: OCR, parsing, extraction, normalization, rendering, aggregation, translation or model interpretation;
- `collection`: connector, API session, download/import batch or capture receipt.

Edges (typed and directionally validated):
- `issued_by`: artifact → origin;
- `signed_by`: artifact → origin;
- `derived_from`: artifact → artifact;
- `copied_from`: artifact → artifact;
- `produced_by`: artifact → transformation;
- `consumes`: transformation → artifact;
- `depends_on_origin`: origin → origin (shared provider/common upstream);
- `retrieved_via`: artifact → collection.

The input schema does **not** admit caller assertions such as `independent_of` or `same_origin_as`. Those are evaluator-derived results, never source facts.

## Namespaced origin identity

Origin identity is resolved from a tuple of:
- issuer namespace and issuer ID;
- source-system namespace and source-system ID, when known;
- legal-entity/account scope where relevant;
- source profile/version;
- identity qualification state and evidence reference.

Local IDs are never globally unique. Two different banks may both have a source system called `core-ledger`; that does not make them one origin. Conversely, two IDs under one qualified issuer/system do not become independent merely because the identifiers differ.

Issuer identity and source-system identity are distinct. A supplier statement and invoice may be generated by different systems yet remain evidence from the same supplier-origin for a supplier-asserted billing proposition. A bank statement and CAMT.054 notification are multiple bank artifacts, not independent bank authorities.

## Deriving artifact origins

For each in-scope artifact, recursively traverse:
- direct `issued_by` and `signed_by` edges;
- `derived_from` and `copied_from` parent artifacts;
- `produced_by` transformation nodes and their `consumes` parents.

The resulting set of qualified root origins is purpose-scoped. If an artifact has no resolvable root, report `origin_unknown`; do not invent an origin group. If provenance is contradictory or has invalid/cyclic paths, report `origin_conflict`.

Then merge origin roots when:
- their qualified issuer identity is the same for the proposition under evaluation;
- their qualified source-system identity is the same;
- an explicit common-upstream `depends_on_origin` path binds them to the same provider/dependency.

Collection channel/session is provenance metadata, not an independent origin. Separate channels do not create independence where issuer/system origin is shared.

## Purpose-specific independence

The same two artifacts can have different evidential roles across procedures. The resolver must bind:
- assertion kind;
- intended procedure/purpose;
- proposition/population under test;
- origin and authority scope;
- applicable source profile and evidence frontier.

For bank completeness, two statements from the same bank do not independently corroborate the bank's own full population. For temporal coverage, statements from different months may both be necessary artifacts even though they share the same bank origin. Independence is not a synonym for artifact uniqueness or period coverage.

## Hard graph invariants

1. Node IDs are unique within the graph.
2. Every edge endpoint exists and its node types match the edge contract.
3. Provenance derivation is acyclic; return a concrete cycle path on failure.
4. Every derived/copy artifact binds at least one parent and a qualified transformation/copy reason.
5. Every transformation binds exact input artifact commitments, recipe/version and output commitment.
6. Every in-scope evidence artifact must resolve to one or more qualified roots, or remain unknown.
7. A missing provenance edge is unknown, not independent.
8. Identity conflicts and incompatible namespace claims remain visible.
9. Re-encoded or reformatted files derived from the same parent remain dependent.
10. A mirror artifact cannot increase the independent-origin count.
11. Different collection sessions, file names, MIME types, API endpoints or hashes do not by themselves prove independent sources.
12. Changing a parent artifact or transformation recipe invalidates only dependent provenance and assertion workpapers.
13. Output is deterministic under node/edge arrival-order permutations.
14. The resolver never consumes a caller-provided independence group as authority.

## Dispositions

- `independence_resolved`
- `origin_unknown`
- `origin_conflict`
- `provenance_invalid`
- `provenance_cycle`

The output includes the per-artifact root-origin set, derived origin clusters, independent-origin count, unresolved artifacts and reason codes. It is not a universal trust score.

## Synthetic benchmark v1

The candidate-visible corpus covers 20 scenarios:
1. two different qualified origins, no shared dependencies;
2. PDF and screenshot from one source export;
3. management report and TB from one GL;
4. supplier invoice and statement from one supplier system;
5. supplier invoice and warehouse receipt from separate sources;
6. CAMT.054 and CAMT.053 from one bank authority;
7. bank statement and screenshot from same source;
8. two origins sharing a bank-data aggregator;
9. authenticated direct external confirmation independent of management;
10. same source bytes under different artifact IDs;
11. re-encoded formats from the same parent;
12. OCR with exact parent and recipe;
13. OCR with missing parent lineage;
14. stale ledger snapshot from one origin;
15. source-system ID collision across issuer namespaces;
16. different source-system IDs under same issuer;
17. contradictory issuer/source identity claims;
18. cycle in `derived_from`;
19. missing origin edge;
20. different model prompts but same model/source inputs.

The public oracle is a regression aid, not a hidden holdout. Future model evaluation requires a separate access-controlled evaluator.

## Comparison plan

Matched arms:
- file-count/filename heuristic;
- caller-declared origin groups;
- issuer/system registry rules;
- provenance DAG resolver;
- provenance resolver plus Symthaea candidate relationship analyst, independently verified;
- expert accountant/auditor adjudication.

Measure independent-origin precision/recall, false independence, false dependence, unknown provenance, cycle/dangling-edge detection, transformation completeness, reviewer effort and latency. Do not collapse these into one score.

## Claim ceiling

Passing the synthetic corpus establishes only that the graph resolver implements these stated rules. It does not prove the truth of real-world origin claims, bank authenticity, actual third-party independence, audit sufficiency, ISA compliance or an audit opinion. Professional review remains necessary.

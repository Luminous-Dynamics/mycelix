# PSI-002B3A2P — Pinned RFC 9578 Public-Token Backend Preflight

Status: **SOURCE CANDIDATE / EXPERIMENTAL / NOT EXECUTED / NOT A PASS**

This crate preflights one exact external Rust implementation of RFC 9578 publicly verifiable token type `0x0002` before that dependency is allowed into a Mycelix query-credit authority path.

## Exact candidate backend


The upstream project advertises RFC 9578 support but independent audit is not established by this tranche.

## Why type 0x0002 first

The first adapter target is the publicly verifiable Blind-RSA profile. The contact-discovery Origin can verify with issuer public-key material rather than receiving an issuer private VOPRF verification key.

```text
public verification key available
!= issuer key trusted/current
!= token unspent
!= query credit
```

## External stores only

The preflight implements `OriginKeyStore` and `NonceStore` in this external crate. It does **not** enable or import the backend's `test-utils` feature.

The nonce store is deliberately ephemeral and fresh per verification call. It exists only to exercise the backend's required reserve → verify → commit/release state machine.

A committed nonce in that ephemeral store is not service-wide replay evidence.

The corpus deliberately verifies the same token twice with two fresh ephemeral stores to make that non-equivalence executable:

```text
same token verifies twice with fresh ephemeral state
-> backend cryptographic path works
-> service-wide unspent state NOT established
```

## Exact field binding

A successful preflight parses one exact token and binds:

```text
token type
token artifact SHA-256
RFC nonce SHA-256
challenge_digest bytes
full token_key_id
exact SPKI SHA-256
exact backend source identity
```

The full token key ID must equal SHA-256 of the exact SPKI. A valid but different RSA public key is rejected before backend signature verification.

## RFC 9577 challenge cross-check

The source also builds one Mycelix B3A challenge through both:

1. `psi-privacy-pass-rfc9577-challenge`'s independent encoder; and
2. the pinned backend's `TokenChallenge` implementation.

The exact serialized bytes and SHA-256 digest must match.

This proves API/profile agreement only. It does not prove that an arbitrary received token contains the expected challenge digest; that check remains an explicit input to verification.

## Hostile corpus

The source registers cases for:

- Go-generated public token accepted with externally implemented stores;
- frozen token/SPKI/nonce/challenge identities;
- same token verifying again with a fresh ephemeral store;
- signature mutation rejection;
- token-type substitution rejection;
- expected challenge-digest mismatch rejection;
- trailing token-byte rejection;
- full SPKI/token-key-ID equality;
- valid but different RSA key rejection;
- backend TokenChallenge bytes/digest matching the independent Mycelix RFC 9577 encoder;
- strict authority ceiling.

## Authority ceiling

Even successful execution may establish only pinned-backend compatibility and cryptographic verification of the exact test corpus.

It remains false for:

```text

issuer key trusted under Mycelix policy
issuer key current under Mycelix policy

persistent/durable replay protection

```

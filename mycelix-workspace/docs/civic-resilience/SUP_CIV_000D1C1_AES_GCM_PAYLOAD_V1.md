# SUP-CIV-000D1C1 — AES-256-GCM Payload Reference Profile v1

Status: independent cryptographic reference-vector tranche only. Stacked on exact SUP-CIV-000D1B head `1152251e1b8d09bf69cc2497164a0fc1d58da320`.

This tranche freezes one production candidate payload-AEAD profile and its exact known-answer/adversarial corpus. It does **not** implement product Rust, recipient wrapping, storage, authorization, key custody, or entropy generation.

## Profile

`PayloadAeadProfileV1::Aes256GcmFreshDek = 0x0001`

Parameters:

- AES-256-GCM;
- 32-byte DEK;
- 12-byte nonce;
- 16-byte authentication tag;
- exact `PayloadAadV1` bytes from SUP-CIV-000D1B as AAD;
- one fresh randomly generated DEK per payload ciphertext in production;
- one fresh randomly generated nonce per payload ciphertext in production.

Reference-vector keys and nonces are deterministic fixtures and provide no entropy evidence.

## Strong production law

```text
OnePayloadCiphertext -> OneFreshRandomDEK
```

Therefore the production profile strengthens the generic lifecycle model:

```text
PayloadVersionChanged -> FreshDEK + KeyEpochChanged
CiphertextChanged -> FreshDEK + KeyEpochChanged
CompromiseRotation -> FreshDEK + KeyEpochChanged
```

Recipient-only rewrap/current-epoch recipient addition may retain the exact ciphertext/DEK only when the qualified lifecycle transition permits it.

No production API should expose a generic `encrypt_again(existing_dek, ...)` surface.

## AAD binding

The AEAD receives the exact canonical bytes:

```text
PayloadAadV1 {
    schema,
    aead_profile_id,
    payload_subject_commitment,
    payload_version,
    key_epoch
}
```

It deliberately does not authenticate the mutable recipient set directly. Recipient-wrap context and the full envelope have separate transcripts.

```text
PayloadAadV1 != FullEnvelopeV1
```

## Nonce rule

V1 admits exactly 96-bit nonces.

Production nonces are generated by a CSPRNG. They are not derived from wall time, counters shared across devices, ticket IDs, content hashes, envelope revisions, or recipient identities.

Even though the profile also requires one fresh DEK per ciphertext, nonce handling remains explicit rather than relying on that fact implicitly.

## Exact vector corpus

The checked-in vector file contains:

- one AES-256-GCM known-answer vector using the standard all-zero key/IV/plaintext case;
- three Mycelix vectors whose AAD is independently reconstructed from the 000D1B byte theorem;
- eleven negative authentication/profile cases.

The Mycelix vectors separately cover:

- base payload/version/epoch;
- a fresh key epoch;
- a new payload version with another fresh epoch.

The qualification implementation uses Node's built-in cryptographic API to verify the checked-in expected bytes. Expected ciphertext/tag bytes are not generated dynamically by CI.

## Negative cases

The corpus refuses or fails authentication for:

- wrong DEK;
- wrong nonce;
- altered AAD;
- missing AAD;
- altered ciphertext;
- truncated ciphertext;
- altered tag;
- truncated tag;
- 31-byte key;
- 11-byte nonce;
- use of the 000D1B test-reserved profile range.

## Standards boundary

AES-GCM is the authenticated-encryption mode specified by NIST SP 800-38D. NIST is revising that publication, but as of this subject no replacement final revision exists. This profile deliberately uses a 128-bit tag and a 96-bit nonce, avoiding the short-tag surface NIST has announced it plans to remove.

This tranche does not interpret the reference-vector result as proof of the security of AES, the operating system RNG, endpoint memory handling, or any particular Rust crate.

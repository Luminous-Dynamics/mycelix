Program: Luminous-Dynamics/mycelix#940

Parent executable contract: #1572 / `4cc08b827ca085aef78f737fa7c2bf98eb9c8534`

Symthaea consumer profile: Luminous-Dynamics/symthaea#3817 and successors

## 1. Purpose

Freeze how an implementation of the Phase-E bridge may earn a bounded conformance theorem without allowing self-roundtrip success, a matching digest, or one repository's test suite to stand in for independent protocol qualification.

The governing separation is:

```text
protocol specification
!= producer implementation qualification
!= consumer implementation qualification
!= producer-consumer pair qualification
!= upstream snapshot completeness
!= model validity
```

The bridge should be difficult to implement incorrectly and difficult to overclaim when it is implemented correctly.

## 2. Qualification theorem

A producer implementation may earn only the following bounded theorem:

```text
exact ProductHead
+ exact ProductFrozen dependency graph
+ exact protocol/profile revision
+ independent known-answer oracle
+ frozen positive/rejection corpora
+ parser/resource-safety campaign
+ arithmetic/metamorphic campaign
+ mutation discrimination
+ immutable postflight
+ validated Q001 receipt
= qualified producer implementation for Phase-E bridge v1
```

This does not establish source truth, snapshot completeness, authentication, currentness, Symthaea consumer correctness, model validity, resilience, policy authority, or physical action.

## 3. Independent oracle requirement

The normative producer implementation and its reference oracle MUST NOT share the same implementation path.

The first oracle should be Python standard-library only and MUST NOT:

- import or invoke the Rust crate;
- consume Rust-generated expected constants as its source of truth;
- call a Rust CLI to compute expected bytes;
- copy serialized Rust debug/serde output;
- derive expected commitments from artifacts generated by the implementation under test.

Known-answer inputs and expected canonical bytes/commitments are reviewed fixtures whose provenance is separate from the Rust implementation.

Independence remains bounded: two implementations can share the same misunderstanding of the written specification. Qualification must not claim mathematical independence merely because languages differ.

## 4. Closed-world completeness firewall

The bridge validates semantic closure **inside the supplied envelope**. It does not prove that an upstream exporter supplied every object relevant to the authoritative assessment.

```text
all referenced dependency IDs resolve inside envelope
!= authoritative source exported every relevant dependency
```

Therefore v1 qualification separates:

```text
BridgeInternalClosure
UpstreamSnapshotCompleteness
```

Only the first belongs to the bridge core. A later exporter qualification may establish the second for a named authoritative source and exact export profile.

No bridge PASS may be described as a closed-world authoritative snapshot theorem unless that separate exporter theorem is also bound.

## 5. Producer identity limitation

The v1 envelope carries `producer_repository`, `producer_commit`, and `snapshot_revision` as canonical identifiers. The bridge treats them as exact opaque identifiers, not authenticated repository facts.

```text
producer_commit field matches expected bytes
!= commit exists
!= repository controls that commit
!= producer is authorized
```

A future protocol revision may replace or supplement these fields with an `ExactRef`-style producer revision identity. V1 qualification must not silently reinterpret the frozen grammar.

## 6. Commitment boundary

The v1 SHA-256 commitment establishes deterministic content identity under the exact domain-separated grammar.

It does not establish:

- producer authentication;
- collision impossibility;
- semantic truth;
- authorization;
- trusted timestamping.

Cryptographic authentication remains separately composable through Q002/Xenia or another qualified provider.

## 7. Decode-before-allocation discipline

All attacker-controlled counts and byte lengths MUST be checked against frozen structural limits before allocation, reservation, multiplication, slicing, or nested-loop expansion.

The rejection corpus must include:

- top-level payload larger than 4 MiB;
- declared string length over the field limit;
- truncated length prefix;
- length prefix larger than remaining bytes;
- collection count above each frozen object limit;
- nested dependency/failure-domain/evidence-reference count above its limit;
- count/length arithmetic overflow attempts;
- deeply composed valid-looking near-limit collections;
- trailing bytes after one otherwise valid payload.

The qualification theorem is bounded parser behavior under the frozen limits. It is not a universal no-OOM/no-DoS theorem for every host or caller.

## 8. Canonical decoder law

For every byte sequence accepted as canonical v1:

```text
decode(bytes).encode() == bytes
```

The decoder MUST reject rather than normalize:

- out-of-order semantic collections;
- duplicate identities;
- non-canonical decimal encodings;
- unknown enum tags;
- unsupported protocol/schema/canonicalization versions;
- trailing bytes;
- malformed UTF-8;
- disallowed identifier bytes.

Authoring APIs may normalize unordered semantic input before encoding. The decoder of canonical bytes may not repair malformed wire input.

## 9. Anti-downgrade theorem

An unsupported newer or older protocol/schema/canonicalization tuple MUST fail explicitly.

The implementation may not silently decode with the closest supported version, ignore a version component, or accept `protocol=1/schema=2` as v1 because the remaining bytes happen to parse.

## 10. Decimal edge campaign

The exact-decimal campaign must exercise:

- zero only as `(0, 0)`;
- positive and negative mantissas where the field permits signed values;
- rejection of nonzero trailing-zero encodings;
- scale `0` and scale `18`;
- rejection of scale `19`;
- `i128::MIN` and `i128::MAX` canonical encoding;
- checked scale alignment for comparison/addition;
- rescaling overflow;
- addition overflow;
- stock-partition overflow;
- equality across mathematically equal authoring inputs after constructor normalization;
- decoder rejection of alternate non-canonical representations of that same value.

Physical stock fields continue to reject negative known quantities even though the generic decimal representation is signed.

## 11. Arithmetic must fail closed

Capacity ordering and stock conservation checks MUST use checked exact arithmetic.

No overflow may wrap, saturate, clamp, convert to float, or convert an invalid comparison into `Unknown`.

Conceptually:

```text
arithmetic cannot be established exactly
=> invalid bridge input
```

not a weaker successful state.

## 12. Stable validation discrimination

The fail-fast validation order frozen in #1572 is qualification-relevant.

Each rejection fixture should name the expected first semantic error class. A test that merely observes `is_err()` is insufficient where multiple gates could reject the same malformed fixture.

This makes mutation testing discriminating rather than allowing unrelated later checks to hide a removed earlier gate.

## 13. Positive known-answer corpus

The first producer qualification should contain at least six independently specified positive families covering together:

1. minimal valid envelope;
2. all four `Resolution` variants;
3. canonical decimal/unit/basis edge values;
4. multiple services/dependencies/stocks with canonical sorting;
5. shared failure-domain membership and nested exact references;
6. nontrivial manifest/evidence-reference composition near, but below, structural limits.

For every positive fixture, the independent oracle freezes exact canonical bytes and exact domain-separated SHA-256.

## 14. Rejection corpus

The first campaign should include at least thirty named rejection cases and cover all validation stages, including:

- unsupported versions;
- malformed/oversized IDs;
- duplicate identities;
- noncanonical ordering;
- invalid/truncated lengths;
- nested count overflow/limit violations;
- invalid horizon;
- missing service dependency;
- missing dependency failure domain;
- malformed exact reference;
- invalid resolution/availability tag;
- noncanonical decimal;
- negative physical stock;
- unit/basis mismatch;
- `committed > usable`;
- `usable > nominal`;
- `protected + committed > total`;
- checked-arithmetic overflow;
- payload-size overflow;
- trailing bytes.

Unknown, unresolved, not-applicable, unavailable, and zero remain distinct test states.

## 15. Metamorphic campaign

Required metamorphic properties include:

```text
authoring input permutation
-> same validated semantic object
-> same canonical bytes
-> same commitment
```

while canonical wire permutation is rejected rather than reordered.

Additional relations:

- changing a material exact-ref digest changes canonical bytes;
- `Unknown != Unresolved(reason)`;
- `Unavailable != Unknown availability`;
- adopted floor != scenario demand != delivered service;
- one shared failure-domain ID != two distinct failure-domain IDs;
- changing unit or basis changes canonical bytes even when numeric mantissa matches;
- adding a manifest object changes canonical bytes/commitment.

Fixture-specific commitment sensitivity may be asserted. Qualification must not phrase this as a proof that SHA-256 collisions are impossible.

## 16. Mutation discrimination

The qualification campaign should mutate or simulate removal of each critical gate and require a named fixture to fail the mutant.

Targets include at minimum:

- version check;
- duplicate check;
- canonical-order check;
- horizon check;
- referential-closure check;
- decimal canonicality;
- sign restriction;
- unit/basis comparability;
- capacity ordering;
- stock conservation;
- payload/nested limits;
- trailing-byte rejection;
- commitment domain prefix.

A mutant that merely fails to compile is not counted as a semantic kill unless the target theorem is specifically type-level non-representability.

## 17. Parser fault campaign

The decoder should be exercised with deterministic byte-level corruptions of valid fixtures:

- single-bit flips across header, lengths, tags, IDs, digests, decimals and counts;
- truncation at representative byte boundaries;
- appended junk;
- duplicate element injection;
- length/count inflation;
- canonical-order swaps.

Accepted corruptions are allowed only when they decode to a different valid canonical object and their recomputed commitment correctly identifies those different bytes. They must never retain the original expected commitment by implementation accident.

## 18. Fuzzing boundary

Fuzzing/property tests are supplementary evidence, not completeness proofs.

The first campaign should at least establish:

```text
arbitrary bytes -> no panic in bounded decoder harness
accepted bytes -> roundtrip identity
validated authoring objects -> deterministic encoding
```

under explicitly recorded resource/time budgets.

## 19. Producer qualification stages

The producer line is frozen as staged evidence rather than one opaque green job:

```text
QP0 exact subject / parent / scope / dependency audit
QP1 pinned Rust 1.96 fmt + compile + tests + strict Clippy
QP2 independent Python known-answer byte/commitment oracle
QP3 named rejection matrix
QP4 metamorphic + property campaign
QP5 parser fault/resource-bound campaign
QP6 mutation discrimination
QP7 prepared-byte capsule + immutable postflight
QP8 exact-byte ProductFrozen promotion
QP9 exact-head ProductFrozen execution + validated Q001 receipt
```

A failure at any stage limits the claim to the stages actually demonstrated.

## 20. ProductFrozen discipline

The release process should follow the existing REGEN exact-byte pattern:

```text
authored candidate
-> successful preparation capsule
-> archive + internal digest verification
-> reconstruction over exact qualified parent
-> no manual byte repair
-> checked-in frozen dependency graph
-> exact-head ProductFrozen campaign
```

The promoter has repository mutation authority but no authority to manufacture qualification. The qualifier has evidence authority but should remain read-only.

## 21. Q001 receipt requirements

The producer ProductFrozen receipt should bind at minimum:

- exact ProductHead/tree/parent;
- exact protocol/schema/canonicalization/limits profile;
- exact Cargo.lock identity;
- exact Rust/Cargo/rustfmt identities;
- independent-oracle identity/digest;
- positive/rejection corpus identities;
- named qualification assertions;
- preparation capsule identity;
- result;
- one narrow proposition;
- explicit non-claims.

The receipt is structurally validated by the exact qualified Q001 validator before retention.

`Q001 valid != authenticated`; Q002 remains separate.

## 22. Consumer qualification remains independent

Symthaea must qualify its consumer/import implementation separately against the same frozen positive and rejection corpus.

A producer PASS cannot be inherited by the consumer merely because both repositories use the same prose or fixture archive.

The consumer should independently establish:

- exact supported bridge/profile identity;
- exact canonical byte acceptance/rejection;
- exact input commitment;
- semantic projection into its model input state;
- explicit preservation of unknown/unresolved/not-applicable;
- no hidden network/current-state re-resolution;
- an import receipt linking bridge commitment to model-state commitment.

## 23. Cross-repository pair qualification

Only after producer and consumer independently qualify should a pair campaign establish:

```text
qualified Mycelix producer
+ exact bridge payload bytes/commitment
+ qualified Symthaea consumer
+ exact import receipt
= cross-repo bridge conformance for that exact pair
```

The pair theorem does not automatically transfer to later commits in either repository.

## 24. Identity chain

The end-to-end evidence model keeps distinct identities:

```text
Mycelix authoritative snapshot identity
-> bridge canonical payload commitment
-> Symthaea import receipt
-> Symthaea model-state commitment
-> Symthaea model-run receipt
-> model result / counterexample receipt
```

No identity in this chain substitutes for another.

In particular:

```text
bridge commitment != model-state commitment
model-state commitment != model correctness
model result != observation
model recommendation != authority
```

## 25. Common-mode test risk

A shared fixture corpus improves interoperability but can also create common-mode blind spots.

Therefore the final pair campaign should include at least one independently authored fixture on each side in addition to the shared corpus, then require the peer implementation to consume it under the same protocol rules.

Shared fixtures are necessary interoperability evidence, not sufficient independence evidence.

## 26. Fixture provenance

Every retained fixture set must bind:

- fixture schema/profile revision;
- exact file census;
- per-file SHA-256;
- corpus aggregate commitment;
- authoring/oracle implementation identity;
- expected disposition/bytes/commitment where applicable.

A mutable directory name such as `latest` is not a qualification identity.

## 27. Upstream exporter successor

After producer bridge qualification, the next upstream theorem should be a separately qualified **authoritative snapshot exporter** that proves how adopted Mycelix/domain state is selected and projected into the bounded bridge envelope.

That exporter owns questions such as:

- what constitutes the complete service/dependency snapshot;
- which exact evidence/profile revisions were selected;
- whether referenced authoritative objects were omitted;
- how currentness was evaluated before export;
- which authority selected the adopted service profile.

Those concerns deliberately stay outside the pure bridge codec.

## 28. Deliberate non-claims

A bridge implementation PASS establishes no:

- completeness of upstream authoritative state;
- truth/currentness of referenced evidence;
- legitimacy of adopted service floors;
- authentication of producer identity;
- cryptographic collision impossibility;
- Symthaea consumer qualification unless separately executed;
- model correctness or predictive validity;
- real disaster probability;
- real community/civilizational resilience;
- emergency authority;
- procurement/investment authority;
- physical-action authority.

## 29. Exit criterion

This qualification profile is ready to authorize executable bridge implementation only when review agrees that future PASS language will remain bounded to:

> the exact producer ProductHead correctly implements the frozen Phase-E bridge v1 canonicalization, validation and commitment contract for the exact qualified corpus and environment recorded in its validated receipt.

Anything stronger requires additional upstream, consumer, pair, scientific, authentication, authority, or deployment evidence.

# PTB DCC 3.3.0 evidence/applicability contract v0.1

Child of [MYC-BUILD-DCC-INTEROP-001 #6047](https://github.com/Luminous-Dynamics/mycelix/issues/6047).

## Scope of this first executable slice

This profile and Rust oracle classify a **normalized synthetic verification report**. They do not parse XML, validate the live PTB XSD, perform XMLDSig cryptography, establish a trust chain, or query SANAS/other accreditation schedules. No crypto code is handwritten. The next parser/verifier adapter must use a vetted implementation and emit a separately reviewable report that conforms to this contract.

## Exact PTB DCC 3.3.0 baseline

- Namespace: `https://ptb.de/dcc`.
- Root element: `dcc:digitalCalibrationCertificate`.
- Required schema version: `3.3.0`.
- Root sequence: required `administrativeData`, required `measurementResults`, optional `comment`, optional `document`, and zero or more `ds:Signature` elements.
- Therefore a document can be well-formed and XSD-valid with **no XML signature**. Absence of signature is not an XSD parse error and must not be classified as authenticated.

Official PTB source: https://www.ptb.de/dcc/v3.3.0/autogenerated-docs/dcc_xsd.html

## Evidence axes are independent

1. Original received bytes and digest/receipt retention.
2. XML well-formedness, namespace, root and schema version.
3. Exact XSD artifact pin and XSD validation result.
4. Signature presence, reference-digest validity, SignatureValue validity and signer certificate status.
5. Signer trust policy and role authorization.
6. Exact signed-reference coverage of every DCC object consumed by the application; no duplicate IDs, external references, disallowed transforms or wrapping ambiguity.
7. Laboratory identity, schedule digest/currentness and exact scope applicability to measurand, method/revision, unit and range.
8. Result-to-passport applicability: instrument/channel/measurand/unit/method/revision/firmware, calibration range/date/due date, sample value/date, uncertainty and correction/supersession lineage.

No single `authenticated` field is sufficient. A valid signature does not prove that the lab's accredited scope covers the method/range. A valid XSD does not prove a signature exists. A valid signed result does not prove the application consumed that same signed result.

## XSD and signature facts

The PTB v3.3.0 XSD makes XMLDSig Signature optional at the DCC root. A normalized report must preserve `xsd_validation_state=valid` independently of `signature.presence_state=absent`. It must return `MORE_EVIDENCE_REQUIRED`, not `REJECTED_DOCUMENT` or authenticated.

The [W3C XML Signature 1.1 Recommendation](https://www.w3.org/TR/xmldsig-core/) separates reference digest validation from signature validation and does not by itself establish signer institutional identity. Microsoft documents XMLDSig security considerations around explicit trust-chain validation, bounded references/transforms and ensuring the application consumes the exact data covered by the signature: https://learn.microsoft.com/en-us/windows/win32/seccrypto/xml-digital-signature-security-considerations.

## Parser/runtime boundary for the next phase

- Preserve exact original XML bytes before parsing; verify signature over the original signed representation, never a normalized reserialization.
- Pin the complete DCC XSD dependency closure by source, version and digest; disable runtime network retrieval, DTD/external entities and remote imports.
- Bound input byte size, depth, node count, signatures, references, transforms and time.
- Reject duplicate XML IDs and ambiguous IDREFs. Disallow external URIs and unsafe transforms by default.
- Bind the parsed result object ID to the object covered by XMLDSig; signed-object/reference coverage must be verified before reading values into Mycelix.
- Use an established independent XMLDSig implementation for differential checks. The `structured-world/xml-sec` project is a candidate to evaluate, not a selected or trusted dependency; pin exact version/source/features and compare against an independent established implementation before use.

## Incumbent baseline

MZW-DCC already documents mapping proprietary calibration XML into DCC-JSON/PTB DCC XML 3.3.0 with offline repeatable mapping profiles. Conversion and XSD-valid serialization are therefore not a Luminous differentiator. The proposed value is **trust-preserving applicability** from original signed bytes through signer trust, lab scope, exact method/range and passport sample binding.

Source: https://github.com/Zwernemann/MZW-DCC

## Disposition semantics

- `REJECTED_SOURCE_INTEGRITY`: original bytes/digest/receipt mismatch or missing retained original.
- `REJECTED_DOCUMENT`: malformed XML, wrong namespace/root/version, or pinned XSD validation failure.
- `REJECTED_XML_ID_AMBIGUITY`: duplicate IDs or invalid reference identity.
- `REJECTED_EXTERNAL_REFERENCE`: any external reference attempt under this profile.
- `REJECTED_SIGNATURE_INVALID`: invalid reference digest/signature value, revoked/expired signer certificate.
- `UNTRUSTED_SIGNER`: valid signature from a signer not trusted or not authorized for the calibration role.
- `REJECTED_SIGNATURE_COVERAGE`: the data consumed are not exactly among the signed references, or unsafe transforms/wrapping ambiguity remain.
- `MORE_EVIDENCE_REQUIRED`: XSD/schema bytes not pinned, signature absent/unknown, signer/lab schedule unknown, uncertainty incomplete or correction state unresolved.
- `NOT_COMPARABLE`: exact lab scope, measurand/unit/method/range or passport subject mismatches.
- `EXPIRED_OR_INVALIDATED`: sample outside calibration range/time, out-of-tolerance result or superseded certificate.
- `ELIGIBLE_FOR_INDEPENDENT_PASSPORT_REVIEW_ONLY`: all synthetic gates align. It is not cryptographic verification performed by this oracle and not passport admission.

## Claim ceiling

All 36 cases are synthetic. This PR does not parse real DCC XML, validate the actual XSD bytes, verify any real signature/trust chain, authenticate a laboratory, confirm SANAS scope, or qualify an instrument. The XSD bytes are deliberately marked not yet pinned; no schema-validation PASS is implied.

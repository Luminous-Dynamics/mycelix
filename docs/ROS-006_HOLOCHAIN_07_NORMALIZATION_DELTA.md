Audit date: 2026-10-01  
Branch: `feat/ros-006-qualification-boundary-v2`  
Status: **pre-migration delta; no 0.7 source or lockfile mutation performed**

## Why this exists

The source inventory identifies where the 0.6 → 0.7 action-model migration will occur. This document adds the dependency-level delta so that the next implementation pass can be executed as a controlled graph migration rather than a sequence of ad-hoc version edits.

Holochain's official 0.7 compatibility table currently identifies Holochain 0.7.0, HDK 0.7.0, HDI 0.8.0, Lair 0.7.1, JS client 0.21.0, and Rust client 0.9.0 as the compatible generation.

## Important delta: serialization

`holochain_serialized_bytes = 0.0.57` is already correct for the 0.7 migration and should not be treated as a required version change.

The official upgrade guide specifically calls out 0.0.57 because `hdi` requires it exactly.

## Important delta: Holochain feature flags

Where the repository has explicit Holochain dev-dependency features, inspect for:

- removed `sqlite-encrypted` → `encryption`
- removed `wasmer_sys` → `wasmer-sys-cranelift`
- removed `transport-iroh` because iroh is now built in

These are source/manifest migration items, not candidates for blind global replacement.

## Nix / Holonix discrepancy

`mycelix-workspace/flake.nix` currently contains:

`github:holochain/holonix/d21b3543`

The surrounding comment says this commit is controlled by:

`nix/modules/holochain-versions.nix`

but the audited repository does not currently contain that path.

Therefore the next normalization pass should either:

1. establish the referenced version module as the authoritative source and make the flake consume it, or
2. remove the stale comment and make the flake's explicit pin authoritative.

Do **not** silently invent a missing version module during the 0.7 migration.

The actual Holonix 0.7 revision must be selected and locked in the real Nix environment. This document intentionally does not fabricate a commit hash.

## Required implementation order

### Gate A — dependency graph

Create a dedicated 0.7 normalization change set for:

1. unified workspace;
2. civic workspace;
3. commons workspace;
4. Holonix/Nix input;
5. applicable client/tooling manifests;

Then regenerate the locks in the actual 0.7 environment.

### Gate B — compiler fixture

Migrate:

first.

It contains representative:

- create-entry dispatch;
- update dispatch;
- delete dispatch;

A successful compile becomes the template for subsequent zomes.

### Gate C — semantic propagation

Propagate the proven pattern to:

1. emergency-incidents;
2. property-registry;
3. property-transfer;
4. housing-membership;
5. justice-cases.

Preserve application-level validation behavior.

### Gate D — host/runtime evidence

Validate:

- 0.7 conductor startup;
- zome installation;
- validation callback execution;
- deterministic host calls;
- test harness behavior;
- network/bootstrap behavior.

Holochain 0.7 removes tx5/WebRTC in favor of iroh/QUIC, so conductor and network configuration must be treated as a separate migration surface.

### Gate E — identity break

Record the resulting DNA/network identity break explicitly.

Holochain documents that integrity-zome dependency updates change DNA compatibility, and the 0.6 → 0.7 upgrade is a clean break from the prior database/wire protocol generation.

## ROS-006 isolation rule

No dependency normalization should alter:

- `QualificationDependency`;
- `QualificationDependencyObservation`;
- certificate schema/digest semantics;
- resolver determinism;
- Relationship 360 qualification semantics.

ROS-006 should consume the normalized host boundary later.

This prevents a Holochain migration from becoming an accidental qualification-semantics migration.

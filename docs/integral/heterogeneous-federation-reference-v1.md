# Deterministic heterogeneous federation reference model v1

Status: **ReferenceModelOnly**

This tranche extends the Integral/Mycelix semantic seam from a single node to a small heterogeneous federation oracle. It is deliberately independent of transport, Holochain, storage, network timing, and UI implementation.

## Semantic boundary

The model treats these as distinct facts:

- local authority;
- foreign evidence;
- explicit recognition of foreign evidence;
- explicitly delegated foreign authority;
- logical delivery identity;
- transport attempt identity;
- claimed origin identity;
- model-known origin identity;
- schema generation;
- authorization generation;
- authorization expiry;
- source observation;
- privacy-minimized projection.

A foreign artifact never becomes local authority merely because a local node receives, recognizes, summarizes, or displays it. Authority crosses the node boundary only through an explicit `RecognitionEdge` whose mode is `DelegatedAuthority`.

The pure model assumes its caller has already bound the envelope's claimed origin to an authenticated sender identity, the target to the actual receiving node, and the authorization fact to the applicable authorization generation. The envelope fields alone are not authentication evidence. Recognition edges are trusted model inputs, not proof of production governance or authorization. `FederationState::try_new` rejects empty or duplicate node IDs rather than silently selecting one profile, while `new` retains the fixture-convenience API and fails loudly on that malformed input. Recognition edges have an explicit fallible insertion path that rejects empty or unknown identities; exact duplicate edges normalize away. The deserializable semantic input types (`NodeProfile`, `RecognitionEdge`, `FederationEnvelope`, `ObservationRecord`) and structured invariant-audit entries reject unknown JSON fields rather than silently discarding them, so callers cannot smuggle unenforced extension fields across the reference-model boundary.

## Delivery rules

The oracle enforces:

1. transport unavailability produces `PartitionUnknown`, never success;
2. a stale schema or authorization generation fails closed;
3. a duplicate logical delivery is idempotent only when its complete immutable contract matches; transport attempt identity is excluded from that contract;
4. the immutable contract binds logical delivery ID, origin, target, semantic subject, payload commitment, schema generation, authorization generation, predecessor, and expiry;
5. reusing a logical delivery identity with a changed payload or origin is a conflict;
6. reusing a logical delivery identity with any other changed contract field (including target) is a contract conflict and returns no authority; identity conflict classification takes precedence over unknown current target/origin lookup for an already-admitted logical delivery;
7. delayed/reordered causal children remain pending until their predecessor is admitted;
8. exact duplicate recognition edges are canonicalized away, while distinct recognition modes remain a conflict rather than being silently collapsed;
9. reconnect is ordinary replay of the exact logical delivery, not a new authority grant;
10. replay remains subject to the current node activity, schema/authorization generation, and expiry gates, so reconnect cannot revive a deactivated, stale, or expired delivery;
11. an `expires_at` instant is exclusive: delivery is valid strictly before that instant;
12. expired authorization remains expired across reconnect;
13. recognition changes after admission do not retroactively rewrite the authority bound to an existing logical delivery;
14. foreign receipt does not by itself populate `recognized_by`; that field is populated only when a matching recognition edge exists;
15. foreign observations retain their origin node;
16. observation IDs are insert-only: an exact record replay is Duplicate, while reuse with changed fields is Conflict and never overwrites; distinct IDs remain separate observations; a changed logical delivery ID cannot reuse the same observation identity to mint another delivery;
17. the generic observation-write API cannot self-assert `source_observation`; source-observation provenance is minted only by the delivery admission transition;
18. generic observation writes also reject empty identity-bearing fields, preventing empty observation keys from aliasing the ledger;
19. generic observation writes cannot self-assert recognition provenance; recognition provenance is produced only by the federation admission transition;
20. privacy projections are explicitly non-authoritative and cannot become source observations; they preserve whether the displayed origin is only a claim or a model-known node identity. Empty envelope identity fields fail closed before admission and cannot alias the delivery or observation ledgers;
21. federation outcomes, privacy projections, and cockpit projections are reporting outputs only: they serialize for external use but are not deserializable back into the reference model; `FederationOutcome` is additionally opaque outside its accessor API.
22. `ObservationRecord` distinguishes a claimed origin from a model-known origin, and generic observation writes cannot self-assert the known-origin flag.
23. rejected identity and immutable-contract mutations are side-effect-free: they do not append delivery attempts, replace admitted delivery identity/authority, or overwrite the observation ledger;
24. `FederationOutcome.origin_node_known` reflects actual model knowledge, not merely the decision enum: malformed input and an unknown origin remain unproven, while an unknown target does not erase knowledge of an otherwise known origin.
25. a delivery cannot name its own logical delivery identity as a predecessor; self-referential causal edges are rejected before ledger mutation rather than remaining permanently pending.
26. predecessor satisfaction records historical admission, not a fresh authorization grant: later node-state drift on the predecessor does not erase the already-admitted causal dependency, while the child remains subject to its own current activity, generation, authorization, and expiry gates.
27. admitted delivery dependencies are acyclic by construction: a predecessor must already exist before a new delivery is admitted, admitted contracts are immutable, and self-edges are rejected. Consequently, an accepted dependency can only point backward in admission history; attempted back-edges can only conflict with the immutable predecessor contract.
28. exact replay of the same transport attempt is idempotent and side-effect-free: the logical delivery identity, attempt ledger, and observation ledger remain unchanged. A changed attempt identity may extend the attempt ledger only when the immutable logical delivery contract still matches.
29. matching authorization generation never upgrades an explicitly inactive authorization state: `Expired`, `Revoked`, and `Absent` all fail closed, including on replay of an already-admitted logical delivery, without appending a new attempt or rewriting admitted state.
30. reporting types are one-way at the type-system boundary: `FederationOutcome`, `PrivacyProjection`, and `CockpitProjection` implement serialization but not deserialization, so serialized reports cannot be rehydrated directly into those model/report types.
31. transport uncertainty does not erase independent model knowledge: `PartitionUnknown` means delivery is unestablished, but `origin_node_known` remains true when the claimed origin is already a known node and false when it is not.
32. every admitted delivery mints exactly one source observation, while generic non-source observations remain independent; therefore the source-observation ledger count tracks admitted-delivery count even when additional ordinary observations exist.
33. every admitted delivery records the exact source-observation identifier it minted and the recognition provenance captured at admission; that observation must retain the admitted delivery's semantic subject, payload commitment, origin, known-origin status, and admission-time recognition provenance, so the cross-ledger provenance link is explicit without re-evaluating mutable recognition state.
34. `envelope_id` is the source-observation identity for an admitted delivery and is insert-only across the observation ledger; reusing that envelope identity for a different logical delivery is rejected rather than allowing one observation identity to alias multiple semantic deliveries. `FederationOutcome` also cannot be externally constructed because its authority-bearing fields are private; report authority therefore has a single construction path through the federation transition logic.
35. a transport `attempt_id` is bound to the `envelope_id` that first carried that attempt within its logical delivery; replaying the same attempt with a different envelope identity is an `AttemptConflict` with no ledger mutation. New attempt identities may still extend the attempt history when the immutable logical-delivery contract matches, and the attempt-ID set and attempt-to-envelope bindings must remain one-to-one; orphaned attempt-to-envelope bindings are invalid under the executable invariant. Attempt identifiers are intentionally delivery-scoped rather than globally unique.
36. a new transport attempt with a new envelope identity is still a duplicate of the existing logical delivery, but it does not mint a second source observation; the original admission-time source-observation identity remains fixed while only attempt history extends.
37. the source-observation ledger is bijective with admitted delivery links: every admitted delivery links one unique source observation, and every source observation marked as such must be linked by exactly one admitted delivery; orphaned source observations and duplicate delivery links are invalid under the executable invariant.
38. `attempt_id` is scoped to its logical delivery: the same attempt identifier may independently occur on different logical deliveries, but within one logical delivery an existing attempt cannot be rebound to a different envelope identity.
39. `FederationState::validate_state` is a read-only qualification gate with typed invariant failures for delivery-map identity, observation-map identity, source-observation bijection, attempt history/binding integrity, and delivery-to-source-observation provenance. It never repairs corrupted state.
40. `canonical_state_fingerprint` provides an order-independent serialized representation of authoritative federation state for deterministic qualification comparisons. It is comparison evidence, not a cryptographic hash or a production persistence format.
41. The qualification validator also checks the authoritative node map, canonical recognition-edge ordering and node references, delivery origin/target references and identity-bearing fields, predecessor existence/non-self-reference, and an explicit admission-order witness requiring unique contiguous ordinals plus predecessor-before-child ordering. These checks are diagnostic only and do not repair state.
42. The qualification invariant inventory is itself executable: `FEDERATION_INVARIANT_REGISTRY` is the canonical 12-entry registry of invariant IDs, descriptions, predicates, and typed failures, and `validate_state` iterates it directly. The reference table below is documentation of that registry rather than a separately maintained invariant list.
43. Every successful new logical delivery consumes exactly one monotone admission ordinal, while retries, rejected deliveries, and other non-admitting outcomes consume none. The `DeliveryAdmissionOrder` invariant requires those ordinals to be unique and contiguous and requires every admitted predecessor to have a strictly earlier ordinal than its child. A causal cycle therefore cannot satisfy the temporal witness.
44. The admission-order witness has a dedicated adversarial mutation corpus with three isolated corruptions: duplicate admission ordinals, an admission-counter gap, and a predecessor that points to a later-admitted delivery. Each must isolate `DeliveryAdmissionOrderMismatch`. All three unordered mutation pairs are exercised in both directions and replayed deterministically, so the temporal witness is tested both as a single-state predicate and under composed corruption.
45. The public transition-preservation corpus treats admission ordinals as a conserved lifecycle resource: valid transition fixtures begin and end with the next admission index equal to admitted-delivery count; transitions that admit nothing preserve the counter exactly; each new logical delivery increases the counter and delivery count by one and receives the prior counter value; and exhausted ordinal space rejects before mutating either the source-observation or delivery ledger.
46. Deterministic state-machine evidence now records each step's pre/post admission index, pre/post admitted-delivery count, and exact newly admitted `(delivery_id, admission_index)` pairs. Valid traces require the counter delta to equal the delivery-count delta and the newly assigned ordinals to equal the consumed contiguous range; the same fields are included in invariant-failure capsules for replay and diagnosis.
47. Successful trace capsules now persist the complete per-step state-machine evidence, including the step token and admission evolution. Capsule validation checks operation/token alignment, temporal delta consistency, and exact equality with a fresh replay of the canonical plan, while dedicated regression coverage rejects temporal-evidence tampering. This makes a passing trace a portable, self-validating evidence artifact rather than only a compact reproduction descriptor. Invariant-failure capsules likewise use a strict top-level schema boundary, rejecting unknown JSON fields rather than silently ignoring schema extensions.


48. Successful trace capsules now have two distinct verification layers. The first is an evidence-only verifier that does not execute federation transitions: it checks schema and integrity metadata, the canonical trace descriptor, state-fingerprint continuity, explicit admission-index and delivery-count continuity between adjacent steps, monotone deltas, exact consumed admission ordinals, chain linkage, and terminal-state agreement. The second layer remains the stronger semantic replay check against a fresh execution of the reference transition path. Regression coverage deliberately re-seals a capsule after forging a cross-step temporal boundary and proves that the evidence-only verifier rejects the internally rehashed artifact; this prevents the digest layer from becoming a substitute for semantic evidence.
49. The successful trace capsule schema now carries an authenticated `verification_profile` identifier distinct from the hash algorithm/encoding metadata. The profile participates in the trace-body hash view and is checked before evidence acceptance, so schema evolution and verifier-semantic evolution have separate identities. This is deliberately not an authorship or authenticity claim: an actor capable of rewriting the artifact can still recompute its digest, while a future verifier can at least reject artifacts produced under an unsupported verification contract rather than silently applying different semantics.
## Qualification validator
The validator deliberately mirrors the reference model's canonicalization boundary: recognition edges are checked in their normalized order, while semantic state is checked for key/relationship consistency. This follows the same broad separation seen in provenance validation, where uniqueness, ordering, and impossibility constraints are checked independently from normalization/equivalence.


The executable invariant layer is exposed as a typed, observational qualification boundary. The Rust implementation maintains one canonical `FEDERATION_INVARIANT_REGISTRY` containing the invariant identifier, human-readable name, description, semantic dependencies, executable predicate, and typed diagnostic. `validate_state` iterates that registry directly, so the invariant inventory and executable qualification path cannot silently diverge. The registry is also required to be a topological ordering of its dependency graph: derived checks must appear after the checks whose validity they rely on.

The executable invariant layer is exposed as a typed, observational qualification boundary. `validate_state` rejects the first detected invariant violation without mutating state, allowing callers to distinguish a valid admitted state from specific classes of cross-ledger corruption. `validate_state_all` provides the corresponding compact audit form: it still evaluates every predicate and returns every violated invariant in deterministic registry order. `audit_state` additionally returns a fixed-length status vector covering every registered invariant, including explicit `Passed` entries, making complete qualification evidence stable even when the corruption surface changes. Dependency metadata documents and regression-tests semantic ordering without suppressing derived diagnostics; this preserves the useful distinction between independent corruption and corruption that cascades into a derived check. `canonical_state_fingerprint` provides a deterministic comparison representation over the authoritative node, recognition, delivery, observation, and admission-order witness state; it intentionally does not claim cryptographic properties.

## Cockpit seam

`CockpitProjection` is intentionally a projection DTO rather than a source of truth. It exposes enough information for a Leptos cockpit to distinguish:

- local authority;
- foreign evidence;
- explicitly delegated foreign authority;
- origin;
- logical delivery identity;
- transport attempt identity;
- semantic decision;
- the reason for the decision.

A future UI adapter must render these distinctions without collapsing them into a single status, trust score, or authority indicator.

## Transition preservation evidence

The executable transition corpus validates the authoritative state immediately after each exercised public state transition. It covers successful recognition insertion, exact duplicate recognition, rejected unknown-node recognition, ordinary observation insertion/duplication/conflict, local admission, a duplicate replay with a new transport attempt, attempt/envelope rebinding rejection, partition uncertainty, stale generation, expiry, revoked and absent authorization, and a forged source-observation claim. Each transition is followed by the full invariant gate; rejected paths additionally require the canonical authoritative-state fingerprint to remain unchanged. This establishes transition-level preservation for the encoded corpus rather than relying only on post-hoc corruption detection.

The transition helper also snapshots the admitted-delivery identity set, delivery count, and admission counter around every transition. It requires non-admitting transitions to preserve the counter, requires a single successful admission to advance the counter and delivery count together by exactly one, and verifies that the newly admitted delivery receives the consumed ordinal. The admission allocator uses checked addition and has a fail-closed regression at `u64::MAX`; the exhaustion path must leave the delivery ledger, observation ledger, counter, canonical fingerprint, and full audit vector unchanged.

The state-machine trace runner applies the same principle to each generated step: before executing the operation it snapshots the admission counter and delivery identities, and after execution it records the resulting counters plus every newly admitted delivery and its assigned ordinal. This turns admission evolution into replayable evidence rather than an inference from the final fingerprint alone.

The broader mutation evidence has two complementary layers: 12 single-fault mutations demonstrate distinguishable invariant failure surfaces, while the full 66 unordered invariant-pair matrix checks deterministic composition in both mutation orders. The pairwise corpus explicitly records the one intentionally destructive interaction between deleting attempt history and injecting an orphan binding; this is characterized rather than normalized away.

## Transition-sequence evidence

The test module also contains a bounded deterministic state-machine corpus with 64 traces of 64 operations each. Operation selection uses a fixed 64-bit recurrence and records the exact operation, semantic decision/authority when applicable, and canonical authoritative-state fingerprint at every step. The same trace is executed twice and the complete evidence vectors must match exactly. Every step then passes the full invariant registry, so the check is temporal across the operation sequence rather than only a final-state assertion. The corpus includes successful admissions, exact replay, new-attempt replay, attempt rebinding rejection, local and foreign admission, recognized foreign admission, causal pending/admission, recognition mutation, ordinary observation insertion/duplicate/conflict, partition uncertainty, stale generation, expiry, revoked/absent authorization, source-claim forgery rejection, and existing-delivery payload conflict. Operations with meaningful preconditions synthesize only the minimum prerequisite state needed to exercise the intended transition, making the generated sequence corpus total rather than silently skipping unsupported operations.

This is deliberately implemented without introducing another testing dependency. It is deterministic state-machine exploration, not randomized property testing or a claim of exhaustive state-space coverage. External Rust state-machine tooling can provide generated sequences and shrinking when a dependency budget permits; the current corpus prioritizes zero-dependency reproducibility and exact trace replay.

Each generated sequence also has a versioned (schema `5`), self-validating JSON trace capsule containing the canonical trace index, initial seed, operation sequence, per-step tokens, explicit initial and terminal state witnesses, full per-step execution evidence, and an integrity record. Every evidence entry carries an explicit step index, pre-state fingerprint, post-state fingerprint, admission evolution, and exact newly admitted delivery/ordinal pairs. Capsule validation checks generator identity, step ordering, state-fingerprint continuity, admission/delivery deltas, contiguous consumed ordinals, terminal-state agreement, and exact equality with a fresh execution replay. Tampering with the schema version, seed, operation, token, step identity, state boundary, or temporal evidence is therefore rejected before the capsule is accepted as a faithful record. The capsule, boundary, and per-step evidence records also use strict deserialization, so unknown fields are rejected instead of being silently ignored. This makes a successful trace a portable, replayable temporal evidence artifact rather than merely a reproduction descriptor. The capsule remains a test/evidence surface, not authoritative persisted federation state and not a cryptographic attestation. Schema `5` also carries an explicit `verification_profile` identifier (`integral-federation-state-machine-trace-v1`) inside the authenticated trace body, so future verifier semantics cannot silently reinterpret the artifact under the same schema. It additionally carries a SHA-256 integrity digest over a separate trace-body hash view and a per-step SHA-256 chain. The chain starts from a fixed genesis marker and each step hashes its explicit predecessor-chain value plus its step evidence, making insertion, deletion, or reordering detectable from the chain head. The declared `serde-json-struct-order-v1` encoding is intentionally local to this Rust evidence format; neither digest establishes authorship, authenticity, authorization, or a cross-language canonical JSON standard such as RFC 8785.

A dependency-free delta-debugging shrinker is also exercised against a representative failing sequence. It repeatedly removes contiguous chunks while the supplied failure predicate remains true, then checks one-minimality by attempting every single-step deletion. The shrinker is generic over the failure predicate, so a future invariant counterexample can be reduced without coupling the production reference model to a particular testing framework. This is sequence minimization evidence, not a claim that every possible failure has been globally minimized.

The invariant-failure path performs a second deterministic minimization pass over the explicit step token used by the state-machine harness to derive operation identities and fixture data. Candidate tokens are drawn from a canonical bounded set plus simple monotone reductions of the current value; a replacement is accepted only when the same failing step, invariant-violation set, decision classification, and authority classification reproduce. The parameter pass first tries independent replacements and then deterministic linked-token substitutions for repeated token values, so coupled fixture identities can shrink together when their relationship is part of the failure. It iterates to a fixed point rather than making only one sweep, and the regression checks that no permitted lower independent or linked candidate still reproduces the predicate. Because each candidate is replayed through the real state-machine transition path, token shrinking cannot silently discard the operation's preconditions. The direct corruption regression reduces (AdmitLocal, 4096), (InjectDeliveryMapCorruption, 4096) to (AdmitLocal, 0), (InjectDeliveryMapCorruption, 0) while preserving the exact DeliveryMapIdentity failure surface. A separate shrinker regression demonstrates the same mechanism converges to a shared token of 1 when zero is semantically invalid. This is parameter minimization for the harness's explicit token parameter, not a claim of globally minimal arbitrary payload semantics.
## Failure evidence boundary

When the bounded state-machine detects an invariant failure, the test emits a machine-readable failure capsule rather than only a human-oriented assertion. The capsule contains a schema version, failure kind, the originating canonical trace index, the exact raw trace prefix through the failing step, the exact operation and token, expected and observed state-validity flags, every observed invariant violation plus the complete audit vector, expected/observed decision and authority where a semantic decision exists, and pre/post canonical state fingerprints. The expanded schema also records pre/post admission indices, pre/post admitted-delivery counts, and the exact newly admitted delivery/ordinal pairs observed at the failing step; the schema version is `2`. The raw prefix is retained directly so a minimized counterexample remains replayable even after it is no longer identical to the original generator output. Canonical generated trace capsules retain the separate generator-validated seed/operation/token descriptor; failure capsules preserve the actual minimized sequence explicitly. The failure-capsule boundary is itself qualified: only the supported schema version and failure kind are accepted, the failed-step index and operation/token must agree with the retained prefix, the audit vector must exactly match the executable invariant registry in canonical order, and the explicit violation list must equal the violated entries derived from that audit vector. The capsule also requires the expected/observed validity flags to describe an actual invariant failure, and its admission-index/delivery-count deltas plus newly admitted `(delivery_id, admission_index)` records must form a contiguous, conserved temporal witness. Unknown top-level fields are rejected at deserialization, so schema evolution cannot silently add unenforced evidence fields.

The failure path first invokes the deterministic sequence shrinker against the observed invariant-violation surface and only accepts a smaller sequence when the same violations, operation, and token are reproduced. It then applies the token-parameter shrinker without requiring the token itself to remain fixed, while preserving the same failed step, invariant-violation set, decision, and authority classification. The parameter pass reaches a fixed point over its declared candidate relation rather than depending on the order of a single sweep. The resulting capsule is therefore a two-stage minimized local counterexample for that failure predicate; direct regression verifies the expected two-step sequence reduction, token reduction to zero, fixed-point behavior, replayability, and rejection of every one-step sequence deletion.

The capsule is intentionally a self-validating evidence/debug surface, not an authoritative persisted federation state format and not a cryptographic attestation. Its purpose is to make a future counterexample portable, replayable, and diagnosable without changing the model's ReferenceModelOnly claim ceiling.

50. Replay-independent trace verification failures are typed (`FederationStateMachineTraceEvidenceViolation`) rather than encoded as message parsing. This preserves stable machine-readable failure classification while the model-coupled replay path remains the stronger semantic check.

51. The next external-trust seam is intentionally specified but not embedded as a self-asserted field in the current capsule. A future checkpoint record should publish at least the verification profile, covered step range, terminal chain head, body digest, and predecessor checkpoint reference through an independently retained Mycelix/federation trust surface. Monitors could then compare successive checkpoints for append-only continuity and request only the affected evidence segment when auditing a trace. This follows the useful part of transparency-log design: independently retained checkpoints and consistency proofs create an audit relationship across published states, whereas a locally recomputed digest alone remains rewriteable by whoever controls the artifact. No current schema-4 field claims such an external anchor exists.

52. The replay-independent evidence verifier also conserves admitted delivery identity: every recorded newly admitted delivery ID must be non-empty and unique across the entire trace. This prevents a self-consistently rehashed capsule from assigning two admission ordinals to the same logical delivery identity. The check is intentionally artifact-local; proving that the identities correspond to actual transition-created records still requires semantic replay.


53. Schema `5` domain-separates the two SHA-256 constructions used by the trace artifact. The capsule-body digest and each evidence-chain digest carry distinct fixed hash domains both in their serialized hash views and at the hash-input boundary. The delimiter is explicit and the domain strings are constrained not to contain that delimiter byte. This prevents accidental cross-purpose reuse of one digest construction as another while keeping the profile/version boundary explicit.

54. The trace checkpoint receipt is now executable in the evidence harness rather than only specified as future architecture. Its half-open coverage ranges are chained contiguously from step `0` to the terminal evidence step; the first receipt references checkpoint genesis; each later receipt binds the exact prior checkpoint digest and chain head; and each receipt independently binds the trace body digest and verification profile. The receipt has its own domain-separated SHA-256 construction and strict deserialization boundary. These checks establish receipt consistency and append-only continuity for the encoded artifact; they do not establish external authorship or authenticity until a separately governed system retains or attests the checkpoint.

## External checkpoint receipt seam

## Publication equivocation witness
The witness layer also has a complete set form for multi-way forks. Given a qualified collection, the collector partitions publications by the full successor namespace (publication profile, hash construction, publication schema, trace profile/schema/identity, and predecessor), deduplicates exact publication replays by publication digest, and emits every unordered pair of distinct successors within each conflicting group. The resulting witness list is canonically sorted by witness digest.

The witness-set artifact has its own strict schema/profile and domain-separated digest over the ordered witness digests. Validation checks every concrete witness against the supplied publication snapshots and then recomputes the complete expected witness list from the collection. Thus omission, duplication, or reordering of a conflicting pair cannot be hidden behind a re-sealed set digest. A three-way fork necessarily yields three pairwise witnesses rather than one arbitrarily selected conflict, preserving complete local fork evidence while remaining deterministic.

The witness set now also carries a versioned commitment to the exact qualified publication collection: the unique publication digest count and a domain-separated SHA-256 over the canonically sorted publication digests. Validation recomputes that commitment from the concrete collection before accepting the witness set. This prevents a witness artifact from being silently reused with a different collection scope, while exact replay of an already-seen publication remains semantically idempotent. The commitment still does not prove that the supplied collection is globally complete; an independently retained collection root or equivalent external witness is required for that stronger claim.

The builder also distinguishes "no equivocation detected" from an empty collection, so absence of a conflict cannot be confused with failure to qualify any publication input.

This is intentionally stronger evidence coverage and scope binding, not a stronger authenticity claim. A monitor that independently retains the qualified collection can therefore preserve and later re-check the exact conflict surface represented by the witness set, analogous to the independent-monitoring role described for Certificate Transparency. citeturn895347search0turn895347search2


The publication-set fork detector now has a portable witness form for a detected split view. The witness binds the publication schema/profile, hash algorithm/encoding, trace schema/profile and trace identity, the common predecessor publication digest, and the two distinct successor publication digests. Its own schema, profile, serialization, and SHA-256 digest are strict and domain-separated. The witness constructor canonicalizes the two successor digests, so exchanging their arrival order cannot change the evidence artifact.

Witness verification is deliberately snapshot-bound: both concrete publication records are revalidated against their trace capsules before the witness bindings are accepted. A caller therefore cannot manufacture an equivocation witness merely by naming two digests. Exact publication replay is not equivocation because the two successor digests must differ, while a changed predecessor or trace namespace is rejected rather than being collapsed into the same fork class.

This strengthens the distinction between detection and evidence. The collection detector answers that two valid publications claim different successors of the same predecessor; the witness preserves exactly which predecessor and successors constituted that observation. It remains ReferenceModelOnly: the witness proves that the supplied artifacts are internally valid and mutually conflicting, but it does not identify an external signer or establish which view is authoritative.

### Cross-view publication reconciliation

Two independently supplied publication collections can now be reconciled without assuming that either collection is globally complete. The reconciliation receipt commits to both collection roots, classifies the exact set relationship as ExactMatch, LeftStrictSubset, RightStrictSubset, OverlappingDivergence, or Disjoint, and records the exact shared and side-only publication digests. It also recomputes the complete equivocation-witness digest list over the union of the two qualified collections. Thus two observers that each saw a partial, individually valid view can expose a fork that neither view contained alone, while a strict subset is preserved as an observation-coverage difference rather than mislabeled as equivocation.

The reconciliation result is permutation-invariant and itself domain-separated/digest-bound. Exact duplicate publications remain idempotent, while changing either collection scope changes its committed root and therefore the reconciliation artifact. This is a gossip-like semantic primitive, not a proof of observer independence: the reference model can prove that two supplied collections agree or disagree, but it cannot prove who retained them, when they were retained, or that two observers were operationally independent.

The receipt also distinguishes set containment from historical continuity. A strict publication-digest subset is only labeled `LeftStrictPrefix` or `RightStrictPrefix` when both supplied collections form validated, genesis-anchored, contiguous publication lineages and the shorter chain is an exact prefix of the longer chain. Two such lineages that share a root and then select different successors are `DivergentAfterCommonPrefix`. A collection that overlaps another but is missing an ancestor or otherwise cannot establish a complete anchored chain is `NotComparable`, preventing incomplete retention from being presented as a valid older checkpoint view.

This follows RFC 9162's security discussion: different clients comparing their published log views can detect conflicting views ("gossip"), but the mechanism itself is not fully specified there. The present layer makes the comparison and resulting evidence deterministic without importing a production gossip protocol or a trust root. citeturn923870view0


Schema `5` now has a separate, non-capsule checkpoint receipt used by the deterministic evidence harness. The receipt itself is checkpoint schema `1`. It binds its own stable checkpoint-profile identifier in addition to the covered trace's verification profile. It also binds a verification profile, trace identity, a half-open evidence range `[step_start, step_end)`, the trace body digest, the chain value immediately before the covered range, the terminal chain value of the covered range, a predecessor-checkpoint digest, and its own domain-separated SHA-256 digest. Checkpoints therefore provide a compact external receipt over an existing trace without adding another producer-controlled trust field to the capsule.

A receipt chain is valid only when its ranges are contiguous from step `0` through the trace length, the first receipt starts from checkpoint genesis, every later receipt names the exact previous receipt digest, every later receipt's chain-start value equals the previous receipt's terminal chain value, and the final receipt covers the trace terminal step. JSON round-trip and adversarial coverage show that reordering, range gaps, and re-sealed predecessor forgery are rejected.

The receipt is still not an authenticity mechanism. It becomes an external trust anchor only when a separately governed system retains, signs, witnesses, or otherwise constrains the checkpoint value. This follows the useful property of Certificate Transparency, where independently retained signed tree heads and consistency proofs let monitors audit append-only behavior; a locally recomputable receipt alone does not provide that property. The current checkpoint is intentionally a linear-chain receipt, not a Merkle inclusion/consistency proof; its dedicated checkpoint profile and distinct genesis marker keep this receipt namespace separate from the trace's verification and evidence-chain namespaces. It is therefore a fixed-artifact receipt: a later growing snapshot cannot be treated as append-only merely because it has a new body digest.

The evidence harness now has a separate checkpoint-publication seam for that case. A publication binds its publication profile, trace schema version, trace verification profile, trace index, covered evidence endpoint, snapshot body digest and chain head, predecessor publication digest, an explicit hash algorithm (`sha-256`) and hash serialization identifier (`serde-json-struct-order-v1`), and its own publication-profile/domain namespace. The trace schema version, algorithm, and serialization identifier are included in the publication hash view so an independently archived publication remains self-describing about which trace artifact schema and digest construction it was issued against; changing either hash metadata is a typed validation failure. Given two snapshots, the consistency verifier requires the later publication to extend rather than roll back the earlier evidence endpoint and requires the later snapshot's initial seed/state/profile plus the complete operation, token, and per-step evidence prefix through the earlier endpoint to match exactly. Publication validation also requires the concrete snapshot to pass the replay-independent trace-evidence verifier, so a caller cannot re-seal an internally inconsistent snapshot and obtain a superficially valid publication receipt. This is a linear prefix-consistency proof between two concrete snapshots; it detects history rewriting without requiring a Merkle tree. The publication is still not an authenticity mechanism: an independently retained or attested predecessor publication remains necessary to constrain who can rewrite the published sequence. After the individual publication records have been validated against their concrete snapshots, a collection-level fork check can additionally detect equivocation when two distinct successor publications claim the same publication schema/profile, hash construction, trace schema/profile, trace identity, and predecessor. Exact duplicate publication replay is not treated as a fork; records from distinct schema namespaces are likewise not conflated as successors of the same lineage. This is evidence of conflicting views, not by itself proof of which view is authoritative.

The fork check is intentionally separate from prefix consistency. Prefix consistency answers whether one concrete later snapshot extends another; fork detection answers whether a set of collected publication receipts contains multiple successors from the same predecessor. The publication-only fork detector is deliberately a narrow primitive and assumes its records have already been validated against their concrete snapshots; the adjacent qualified-collection wrapper makes that precondition executable before invoking the detector and rejects an empty collection. The wrapper canonicalizes its validation order using the complete serialized snapshot/publication entry, so even first-failure diagnostics are permutation-invariant. This prevents a no-fork result, including the vacuous result for zero records, from being mistaken for full publication validity. The set result is permutation-invariant: publication arrival/archive order cannot change whether the collection contains a fork. Together these checks expose both history rewriting and split-view/equivocation patterns at the receipt layer. The ordered publication-chain verifier adds one more boundary: the first collected publication must be rooted at the dedicated publication genesis, and every adjacent pair must pass prefix consistency. This prevents an otherwise valid suffix from being accepted as a complete publication lineage without a declared root. Publication validation also rejects unsupported trace-capsule schema versions before a publication can participate in a lineage, so changing the artifact schema cannot silently pass under an otherwise matching verification profile. The publication schema itself now carries the validated trace schema version into the authenticated publication hash, keeping the archive's binding explicit rather than requiring a verifier to infer it solely from the fetched capsule.

The cross-snapshot relation is also represented as a first-class consistency receipt. It binds the trace schema/profile and trace identity to both the earlier and later publication digests and to their covered evidence endpoints, explicitly declares the proof purpose `append-only-prefix-consistency-v1`, and declares the `sha-256` algorithm and `serde-json-struct-order-v1` serialization used by its authenticated hash view. Those hash metadata fields are themselves digest-bound and are rejected when altered, with its own domain-separated digest and strict deserialization boundary. The receipt is a compact record of the already-verified relation; it does not replace the semantic prefix verifier and does not create external authenticity by itself. Its artifact boundary is independently qualified through deterministic JSON round-trip plus schema/profile/digest tamper rejection. An equal evidence endpoint is treated as the same checkpoint state: the committed body and chain head must also match, while a genuinely advancing publication must move the endpoint forward. This mirrors the stronger equal-size semantics of transparency-log consistency proofs. This follows the separation in RFC 9942 between a receipt that conveys a proof about a VDS and the underlying proof verification process.

This distinction mirrors the stronger append-only property sought by transparency logs: Certificate Transparency uses consistency proofs between tree heads so a later tree can be checked against an earlier advertised tree, rather than trusting a newly recomputed digest in isolation. The current Mycelix receipt is intentionally simpler and explicit about that boundary. A later transparency service can publish these receipts or replace/augment them with a Merkle structure without changing the core trace evidence contract. W3C PROV's treatment of provenance records as things that can themselves have provenance is a useful conceptual parallel for this separation of evidence from its independent provenance.

The complete-lineage validator additionally enforces a single-lineage identity invariant: every unique publication must share one publication schema/profile, hash construction, trace schema/profile, and trace identity. This prevents a publication from an unrelated trace namespace from attaching itself to an otherwise valid root merely by naming that root's digest as its predecessor. Only after that single-lineage identity check does the validator require a unique genesis root and full reachability of every collected publication. Because the qualified collection audit canonicalizes its input first, both successful lineage validation and first-failure diagnostics are deterministic under publication permutation. Exact duplicate publication replays are deduplicated by publication digest before root/reachability analysis, so replaying the same receipt does not create a second lineage node. As it walks the reachable chain, it also runs the concrete cross-snapshot prefix-consistency verifier for every predecessor/successor pair, so a rooted and reachable sequence cannot silently contain a semantically divergent snapshot.

### External evidence anchor references

The reference model now has an explicit evidence-of-evidence boundary for externally retained artifacts. An `FederationStateMachineTraceExternalEvidenceAnchorReference` binds one exact model evidence artifact (for example, a publication-collection reconciliation receipt) to the SHA-256 digest of one externally supplied witness byte sequence, together with the witness kind/profile and a claimed observation time. The reference has its own versioned, domain-separated digest and rejects subject mismatch, witness-byte mismatch, stale self-digests, and unknown JSON fields.

The external witness bytes are hashed from the exact bytes supplied to the verifier. This means the model can establish that a retained witness artifact is the artifact referenced by the anchor record; it still does not establish that the artifact came from an independent observer, that its claimed time is true, or that its internal semantics/signature are valid. Those stronger properties remain the responsibility of an external verifier/retention system.

The anchor metadata now declares the hash algorithm and digest-encoding profile separately for the subject digest and the external witness digest. Both are currently fixed to SHA-256 with the versioned `sha256-lowercase-hex-v1` representation, and noncanonical uppercase hexadecimal is rejected. This prevents a future verifier from silently interpreting the same digest field under a different construction. RFC 4998 similarly makes the digest algorithms used by an evidence record explicit, while RFC 3161 carries the hash algorithm alongside the message imprint; these are useful interoperability precedents for keeping algorithm identity inside the evidence contract rather than implicit in prose. [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html) [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html)

The external witness also carries an explicit schema version, separate from its kind and profile. Version `0` is rejected at construction and validation boundaries, preventing an unspecified witness format from being treated as a qualified external evidence artifact.

This boundary follows established evidence patterns without importing a trust root into the reference model. RFC 3161 defines signed time-stamp tokens over a hash imprint; RFC 4998 defines evidence records for demonstrating data existence over time; RFC 9162 uses signed tree heads and consistency proofs and distinguishes monitor/auditor behavior from the local consistency checks themselves. The present layer deliberately stops one step earlier: it records and verifies the binding to the external witness bytes, but does not pretend to perform TSA, transparency-log, archive-policy, signer, or observer-independence verification. [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html) [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html) [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)

The claimed observation time is intentionally data, not authority. Re-sealing an altered time claim produces a structurally valid reference, which is expected: without an independent time source, the reference model cannot distinguish a real external timestamp from a locally fabricated claim. This keeps the qualification boundary fail-closed instead of converting an internally consistent assertion into a false authenticity or temporal proof.

### External verification statements

An external anchor is now followed by an explicit `FederationStateMachineTraceExternalEvidenceVerificationStatement` boundary when a separate verifier has evaluated the external witness. The statement records the anchor-reference digest, verifier-report schema/profile, the verification claim (such as a validated time-stamp token, transparency consistency result, archive-evidence result, or cryptographic-signature result), the exact verifier-report bytes by digest, and the claimed verification time. The statement has its own strict schema and domain-separated digest.

The statement also binds the anchor reference's schema version and profile, not only its digest. For the current v1 contract these are fixed to the v1 anchor-reference schema/profile and are rejected when altered, even when the statement is deliberately re-sealed. This keeps artifact identity and digest identity coupled rather than asking a downstream verifier to infer the intended contract from a digest string alone.

A composite end-to-end validator now checks the chain in one path: subject metadata and digest → exact external anchor witness bytes → validated anchor reference → exact verifier-report bytes → verification statement. It preserves the underlying anchor diagnostic rather than collapsing any upstream failure into a generic statement error. This makes the intended consumption path harder to misuse: callers do not need to remember to invoke the anchor and statement validators in the correct order themselves.

The composite validator now returns a typed `FederationStateMachineTraceExternalEvidenceVerificationResult` only after the full binding chain succeeds. The result is a read-only projection of the externally asserted claim, anchor identity, verifier profile, verifier-report digest, claimed verification time, and statement digest. It intentionally has no `Deserialize`, no authority disposition, no verifier key/trust root, and no constructor for external callers. A downstream adapter can therefore consume a typed “result reported by verifier X” without being able to rehydrate that result as if it were locally established authority. Re-sealing a structurally valid statement with a different claim changes the typed result rather than being rejected; that behavior is deliberate evidence of the trust boundary, not a verification failure.

The anchor reference, verification statement, and end-to-end binding validator are now part of the non-test federation API rather than existing only inside the test module. The public wire objects retain private fields with strict `deny_unknown_fields` deserialization, and callers receive read-only accessors or a typed result after validation. This makes the exact same semantic verifier available to future RFC 3161, CT, or ERS adapters without maintaining a second runtime implementation.

The stronger `admit_under_policy()` path requires the trust policy to carry an explicit witness kind and witness profile. An unbound policy remains usable only for preflight classification and cannot mint a `FederationExternalVerificationPolicyAdmissionV1`. A mismatch in witness kind or profile is a distinct fail-closed admission result, closing cross-protocol replay where an otherwise accepted verifier/claim pair is applied to an unrelated artifact format.

The external verification statement wire contract is schema/profile **v3**. The schema version was intentionally advanced when verifier identity and freshness semantics were added; legacy statement schemas `1` and `2` are rejected rather than silently interpreted under the new field set. The trust-policy wire contract is now schema/profile **v5**, advanced again when exact verifier-profile commitment binding was introduced. Legacy policy schemas `1` through `4` are therefore rejected rather than being silently interpreted under the stronger semantics. The policy content address covers exact anchor reference (when pinned), exact verifier-profile commitment (when pinned), witness scope, exact verifier identity, identity-use method/profile, and the optional maximum verification age.

Verifier identity is now separately committed as well. Each external verification statement carries a verifier identity kind, identity profile, and SHA-256 identity commitment over adapter-supplied identity material. The statement digest includes all three identity fields, so changing identity necessarily changes statement identity. The local policy can additionally bind an exact verifier identity kind/profile/digest; a matching verifier profile and claim are not sufficient when the identity commitment differs.

### Verifier-profile commitment binding

A verifier profile name is a semantic label, not necessarily an immutable description of the verifier's implementation or configuration. The v5 policy can therefore pin an exact `required_verifier_profile_sha256` commitment over adapter-supplied verifier-profile descriptor bytes. The v3 external verification statement may carry the corresponding `verifier_profile_sha256`, and the admission path rejects both an omitted commitment and a different commitment when the policy pins one. This makes changes to the adapter's declared verifier-profile material visible in both the policy content address and the final admission content address.

The commitment is deliberately not treated as proof of verifier correctness, key possession, trust-root validity, or cryptographic soundness. The profile descriptor remains opaque to the reference model; the adapter defines its semantics and is responsible for authenticating those semantics. The final policy-admission receipt additionally carries an `admission_sha256` content address, and its `validate_integrity()` verifier detects tampering with any recorded decision input. This is an integrity check over the receipt's canonical hash view, not a signature, authorization proof, or replay-prevention mechanism. The stronger constructor `state_machine_trace_external_evidence_verification_statement_with_verifier_profile_evidence(...)` exists so an adapter can bind the exact descriptor bytes to the statement without relying on an unverified caller-supplied digest.

### Versioned wire-shape closure

The external verification statement's v2 serialization is now treated as a closed-world wire contract in the executable conformance suite. The regression enumerates the complete serialized field set and rejects any future addition or removal that is not accompanied by an explicit contract review and schema/profile change. `deny_unknown_fields` continues to protect the deserialization side, while the closed-world serialization assertion protects the opposite direction: a new Rust field cannot silently become part of the public wire representation merely because `Serialize` was derived. This is a wire-compatibility guard, not a cryptographic authenticity mechanism.

### Exact anchor-reference binding

Local policy admission can now additionally pin the exact external-evidence anchor-reference digest. When configured, admission rejects a result whose `anchor_reference_sha256` differs, even when witness kind/profile, verifier identity, verifier profile, claim, and freshness all otherwise match. Because the anchor reference itself binds the subject and witness identities, this provides the missing policy-side material/context boundary: a valid verifier result for one anchor cannot silently satisfy a policy explicitly pinned to another anchor. The binding is optional so reusable policy profiles can remain generic; high-assurance callers can derive an exact-anchor policy for a particular requested evidence context.

### Verifier identity-use binding

Verifier identity naming and verifier identity use are now separate evidence boundaries. The identity-use wire contract is now schema/profile **v2** because it also commits to the exact external verification-statement digest; this contextual commitment prevents otherwise identical identity/report evidence from being replayed across different verification claims or anchor contexts. The new `FederationExternalVerifierIdentityUseStatementV1` commits, independently, to the exact verifier identity material, exact verifier report, and exact binding-evidence bytes, together with a typed binding method and explicit evidence profile. A companion validator recomputes those digests and the identity-use statement digest, while a second validator requires the identity-use statement to match the already-typed external verification result's verifier identity, verifier-report digest, and exact verification-statement digest.

This closes the ambiguity left by an identity commitment alone: a digest can name identity material without demonstrating that the same key or certificate actually authenticated the verifier report. The identity-use statement makes that relationship explicit without claiming to verify the cryptography locally. The statement's contextual digest also prevents a valid identity/report binding from being detached from the particular verification claim and anchor context to which it was originally asserted. Future adapters can supply a protocol-specific binding artifact—for example a CMS signing-certificate relationship for RFC 3161-style evidence, a transparency-log signature binding for CT, or an archive-provider attestation—while the reference model preserves the exact bytes and profile used.

RFC 5035 defines `SigningCertificateV2` as a signed attribute that cryptographically links the certificate used for signature validation and includes a certificate hash (with optional issuer/serial identification). RFC 9162 separately identifies a transparency log by its public key/log ID and uses that key to verify log signatures. These are concrete examples of why verifier identity and proof-of-use are distinct semantic objects. The Mycelix layer records this relationship as external evidence; protocol-specific signature/certificate validation and trust decisions remain adapter responsibilities. citeturn128227search1turn128227search5

The intended composition is therefore:

```text
verifier identity commitment
    ≠ proof that the verifier report was authenticated by that identity

identity-use statement
    = external assertion of that relationship + exact binding evidence

identity-use validator
    = validates identity/report/evidence byte bindings + result correspondence

protocol adapter
    = performs the actual signature/certificate/CT/ERS verification
```

### Policy-bound verifier identity use

Local policy admission now has a stronger optional mode: a policy can require an exact verifier identity **and** an exact identity-use method/profile. In that mode, `admit_under_policy_at()` fails closed rather than silently falling back to identity-only admission; the stronger `admit_under_policy_with_identity_use_at()` path requires the raw identity material, verifier report, use-evidence bytes, and typed identity-use statement.

The resulting admission record preserves the identity-use method/profile, statement digest, and use-evidence digest. The canonical strong path consumes a non-deserializable typed identity-use capability minted only after raw evidence and exact-result correspondence validate; the raw-input API remains as a compatibility wrapper that mints that same capability before admission. The typed admission path re-binds the capability to the exact verification result at the final policy boundary, so a validated identity-use capability cannot be detached from its original claim/context and replayed against another result. The admission record is also content-addressed: its digest covers the exact policy, anchor, verifier, claim, freshness inputs, and identity-use provenance recorded in the decision, giving replay/audit tooling one deterministic identifier for that evaluation output. Both strong paths fail closed when the supplied policy has not explicitly configured an identity-use requirement, so callers cannot accidentally mistake extra evidence for a stronger policy decision. A weak policy remains weak by construction: merely supplying extra identity-use evidence cannot upgrade an unconfigured policy.

This follows the same separation used by the external standards. RFC 5035's `SigningCertificateV2` cryptographically links the certificate intended for validation to signed material, helping detect certificate substitution. RFC 9162 likewise defines immutable log parameters including the public key and Log ID that are used to verify log artifacts. citeturn967539search4turn967539search0

The policy boundary is now:

```text
verifier identity
    → identity-use mechanism/profile
    → identity-use evidence
    → typed external result correspondence
    → local policy admission
```

The identity-use validator still does not perform the actual signature, certificate-chain, CT, or archive cryptographic verification. It verifies that the supplied bytes and typed result correspond exactly, then mints a typed identity-use capability whose private fields prevent downstream callers from constructing or deserializing an unvalidated assertion. The final admission boundary independently re-binds that capability to the exact external verification result; the protocol adapter remains responsible for proving the external relationship itself.

Freshness is an independent admission dimension rather than an implicit timestamp convention. An institutionally bound policy may configure a non-zero `maximum_verification_age_seconds`; `admit_under_policy_at()` requires an explicit evaluation timestamp and rejects evidence from the future, evidence older than the configured maximum age, or any policy that has not explicitly configured a freshness budget. The resulting non-deserializable admission record carries the claimed verification time, evaluation time, and computed age so downstream consumers cannot silently reinterpret the freshness decision.

This prevents a second class of replay: an otherwise exact verifier identity, witness identity, and claim can become inadmissible solely because its evidence horizon has expired. Freshness is therefore part of local policy admission, not part of the external verifier's truth claim.

This mirrors the standards boundary without over-claiming it: RFC 3161 identifies a TSA through its time-stamping certificate/key material and policy, while RFC 9162 gives each transparency log a `log_id` and signs its tree head. The COS layer binds those verifier identities as evidence context; it does not itself authenticate the certificate, key, log ID, or proof. Authentication and protocol-specific cryptographic verification remain adapter responsibilities. citeturn851961search1turn851961search0

The next boundary is local policy admission. `FederationExternalVerificationTrustPolicyV1` is a separate, versioned and content-addressed policy that admits exact verifier profiles, a minimum verifier-report schema version, and an explicit set of non-rejection verification claims. Its classifier returns `Admitted`, `RejectedClaim`, `VerifierSchemaTooOld`, `VerifierProfileNotAdmitted`, or `VerificationClaimNotAdmitted`; these are policy decisions, not proofs. Policy construction and deserialization are fail-closed, accepted verifier/claim sets are canonicalized before hashing, and a sealed `FederationExternalVerificationPolicyAdmissionV1` records the exact policy digest, verifier identity/version, claim, and statement digest that were admitted.

The separation is deliberate:

```text
external verifier evidence
    -> typed external verification result
    -> local verifier-trust policy classification
    -> policy admission record
```

A policy admission must never be interpreted as proof that the verifier actually performed the claimed cryptographic operation. For RFC 3161, the actual verifier remains responsible for the token's message imprint, signature/TSA identity, time and policy checks; for RFC 9162, it remains responsible for signed-tree-head and consistency-proof verification; for RFC 4998, it remains responsible for EvidenceRecord/archive-timestamp verification and preservation context. The COS model records the result and separately decides whether that verifier/result combination is institutionally admissible.

The corresponding verifier only checks binding: that the statement names the supplied anchor reference, that the verifier report bytes hash exactly as declared, that its algorithm/encoding metadata is supported, and that the statement digest matches. It deliberately does not turn `TimestampTokenVerified`, `TransparencyConsistencyVerified`, or any other claim into a locally proven fact. A changed claim can therefore remain structurally valid after intentional re-sealing; that is expected because the reference model has no trust root for the external verifier.

This separation mirrors the actual external protocols. RFC 3161 requires the requester to verify the message imprint, hash algorithm, time-stamp token signature, certificate identifier, timeliness, and applicable policy before accepting a token. RFC 9162 likewise has signed tree heads and a defined consistency-proof verification algorithm, while the resulting audit evidence is distinct from the local statement that an external verifier performed that audit. RFC 4998's verification procedure likewise operates over a concrete evidence record, digest algorithm, and archival timestamp structure. The Mycelix reference layer therefore records those results as externally asserted evidence, then keeps verifier trust and policy evaluation outside the semantic oracle. [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html) [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html) [RFC 4998](https://www.rfc-editor.org/rfc/rfc4998.html)

## Qualification boundary

The tests prove only the deterministic behavior of this reference model for the encoded fixtures. They do not prove:

- transport reliability;
- Holochain correctness;
- production federation safety;
- privacy compliance;
- real-world authority;
- economic, ecological, safety, or human outcomes;
- Integral governance validity.

The model is an executable semantic oracle that runtime adapters can be tested against. It is not a ratification mechanism.


## Delivery record observability

`DeliveryRecord` keeps its authority and provenance bindings private while exposing read-only accessors for the source-observation identifier, admission-time recognition provenance, and attempt-to-envelope mapping. This lets runtime adapters inspect the admitted history without gaining a mutation or construction path.

## Output boundary

`FederationOutcome`, `PrivacyProjection`, and `CockpitProjection` are one-way reporting types. They can be serialized for transport or display, but the Rust API also omits `Deserialize` for these report types, so the one-way boundary is enforced at compile time rather than relying only on caller convention. `FederationOutcome` also keeps its authority-bearing fields private and exposes read-only accessors, so an external caller cannot mint or rewrite an authority-bearing result by constructing the struct directly. Authority must therefore continue to originate in the transition function and admitted state rather than in a rehydrated or fabricated report.

## Deterministic scenario oracle

The executable authorization corpus also covers each explicit non-active authorization state on both fresh admission and replay, proving that generation equality cannot upgrade an `Expired`, `Revoked`, or `Absent` claim. The executable causal model also checks a multi-generation delivery chain and verifies that an attempted back-edge cannot rewrite an admitted predecessor contract. The executable scenario model contains all 22 declared federation mutation variants. Existing logical delivery identities are checked for immutable-contract conflicts before dependency admission, while delayed/reordered cases use distinct child identities; this keeps replay identity classification stable under missing dependencies. The mutation declaration and scenario corpus are generated from one canonical list, while the expected-decision function is exhaustive, so adding a new variant cannot silently bypass scenario classification; the attempt-identity mutation explicitly exercises the `AttemptConflict` decision path. Repeated execution of the same initial state, envelope, and ordered corpus must produce identical scenario results. Rejected identity and contract mutations are also checked against delivery-identity, delivery-attempt, and observation-ledger snapshots, making the no-side-effect boundary executable rather than merely descriptive. Exact attempt replay receives the same three-ledger snapshot treatment, making the distinction between semantic idempotency and new transport attempts explicit. Each attempt is also bound to the envelope identity that carried it; changing only `envelope_id` while reusing an existing `attempt_id` therefore cannot silently create a new transport identity. The executable invariant additionally checks that recorded attempt IDs and their envelope bindings cannot drift out of one-to-one alignment. Recognition-edge insertion order is also non-semantic because the state canonicalizes recognition edges before evaluation; the oracle tests this with an actual foreign-recognition admission path. Rejected mutations must preserve the delivery-identity ledger, delivery-attempt ledger, and observation ledger, while exact retries may change only attempt history and genuinely new logical deliveries create distinct records. Each admitted delivery also carries the exact source-observation identifier and admission-time recognition provenance minted by that admission, and the executable invariant checks that the linked observation matches the delivery's immutable semantic fields and that captured provenance. The source-observation identity is insert-only, so the same `envelope_id` cannot be reused to alias a different logical delivery. The executable bijection check also rejects orphaned source observations that have no admitted delivery link. Later recognition changes do not invalidate or rewrite this historical admission fact. This keeps transport retry state observable without treating it as part of immutable logical identity.


A zero Unix timestamp is invalid for an external verification statement or evaluation time; `0` is reserved as an absent/unset sentinel.

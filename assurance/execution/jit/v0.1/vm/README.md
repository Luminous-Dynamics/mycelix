# JIT-1B Disposable NixOS VM Harness

Status: implementation candidate; Nix execution pending.

JIT-1B extends the qualified JIT-1A admission/controller theorem into a real VM-isolation harness. It deliberately does **not** register a GitHub Actions runner and does not execute ASSURE-002B as JIT qualification evidence.

## Nix base

The standalone JIT flake is rooted at `assurance/execution/jit/v0.1/` so the VM can consume the frozen JIT-0/JIT-1A payload without escaping the flake source tree.

Its nixpkgs input is pinned to the same top-level nixpkgs revision currently used by the Symthaea flake evidence line:

The lock checker binds the exact five-file JIT-1B payload surface; silently dropping a file from the manifest is a qualification failure.

## VM containment candidate

`jit-1b-vm.nix` uses `pkgs.testers.nixosTest` and configures:

- `virtualisation.diskImage = null` — no persistent root disk;
- `virtualisation.mountHostNixStore = false` — no host-store mount;
- `virtualisation.useNixStoreImage = true` — private Nix store image;
- `virtualisation.writableStore = false`;
- `virtualisation.sharedDirectories = lib.mkForce { }`;
- `virtualisation.vlans = [ ]`;
- `virtualisation.restrictNetwork = true`;
- OpenSSH disabled;
- no Docker/Podman service or socket;
- frozen JIT subtree linked read-only from the Nix store.

### Host-exchange elimination

The pinned nixpkgs QEMU VM module normally contributes writable `xchg` and `shared` 9p mounts at `/tmp/xchg` and `/tmp/shared`. A plain `sharedDirectories = { }` does not remove those merged module definitions.

JIT-1B therefore force-overrides the complete shared-directory option to `{ }`. The qualification VM should contain **no test-driver host filesystem exchange mount at all**. Runtime assertions require:

- `/tmp/shared` is not a mountpoint;
- `/tmp/xchg` is not a mountpoint;
- no `9p` or `virtiofs` filesystem is mounted anywhere in the guest.

The test driver still controls the machine over its independent virtio-console shell channel. JIT-1B never calls `copy_from_host` or `copy_from_machine`.

This is stronger than booting with the exchange devices present and unmounting them before subject execution: there is no host-shared filesystem path for candidate code to recover through a remount.

### Subject privilege boundary

The inert subject does not run as root. Every invocation is generated by one `subject_command(...)` helper so the success, replay-rejection, and fresh-boot executions cannot silently drift onto different sandbox properties.

The transient systemd unit applies:

- `NoNewPrivileges=yes`;
- empty `CapabilityBoundingSet`;
- empty `AmbientCapabilities`;
- `PrivateDevices=yes`;
- `PrivateTmp=yes`;
- `PrivateMounts=yes`;
- `ProtectSystem=strict`;
- `ProtectHome=yes`;
- `ProtectKernelTunables=yes`;
- `ProtectKernelModules=yes`;
- `ProtectKernelLogs=yes`;
- `ProtectControlGroups=yes`;
- `ProtectHostname=yes`;
- `ProtectClock=yes`;
- `RestrictNamespaces=yes`;
- `RestrictSUIDSGID=yes`;
- `LockPersonality=yes`;
- `RemoveIPC=yes`;
- `SystemCallArchitectures=native`;
- `RestrictAddressFamilies=AF_UNIX`;
- `UMask=0077`;
- only `/run/jit-1b` writable.

The fixture then verifies the runtime result rather than trusting configuration text alone:

- effective, bounding, and ambient capability sets are all zero;
- the process UID is non-root;
- common GitHub/OIDC/cloud credential variables are absent inside the subject;
- creating IPv4 or IPv6 sockets is rejected by the subject sandbox.

## In-guest fixture

`jit-1b-inert`:

1. proves its privilege/network self-test;
2. atomically creates `/run/jit-1b/consumed` using shell noclobber semantics;
3. fails with exit code `23` when invoked again in the same boot;
4. runs JIT-1A `check_lock.py`;
5. runs JIT-0 `check_spec.py`;
6. runs the JIT-1A admission mutation suite;
7. runs the public policy-guard suite;
8. reruns the JIT-1A payload lock postflight;
9. writes only an inert PASS marker under `/run`.

## NixOS test campaign

The VM test must prove:

- no prior `/run/jit-1b` subject state at first boot;
- no Docker/Podman socket;
- no host-shared 9p/virtiofs mount;
- no common GitHub/OIDC/cloud credential variables in the VM system manager;
- outbound public-network access from the VM fails;
- the exact JIT-1A gates pass under the unprivileged hardened unit;
- subject-side capability and address-family self-tests pass;
- host-exchange absence still holds after subject execution;
- a second invocation through the **same sandbox command constructor** is rejected with `ExecMainStatus=23`;
- a normal root-filesystem persistence sentinel exists before shutdown;
- the first VM is shut down;
- a restarted `diskImage = null` instance has a different kernel boot ID;
- the ordinary root-filesystem persistence sentinel is absent after restart;
- no prior `/run/jit-1b` state exists after restart;
- host-exchange absence still holds after restart;
- one fresh invocation succeeds and emits the PASS marker;
- the second VM is shut down.

The root-filesystem sentinel is deliberate: checking only `/run` would not distinguish an ephemeral qualification VM from a persistent root whose volatile runtime directory happens to reset on reboot.

The NixOS test-driver log is outside guest storage and records both inert-fixture executions around the shutdown/restart boundary.

## Execution command

```text

```

Do not record JIT-1B PASS unless the exact lock-bound candidate builds and this test completes successfully.

## Claim ceiling

A JIT-1B PASS may establish only the registered local disposable-VM isolation/reuse theorem for the exact frozen candidate.

It does **not** establish:

- GitHub JIT runner registration;
- production runner-group routing;
- production GitHub credential containment;
- hosted/JIT equivalence;
- ASSURE-002B qualification;
- JIT-2/JIT-3/JIT-4/JIT-5 PASS;
- merge/deployment/constitutional/governance/political authority.

JIT-1 as a whole is complete only if the exact JIT-1A predecessor remains qualified and the exact JIT-1B VM subject passes its NixOS test campaign.
